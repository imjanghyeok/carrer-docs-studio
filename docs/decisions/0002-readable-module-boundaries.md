# 0002: 읽기 쉬운 코드와 책임별 모듈 경계

## 맥락

포맷 전용 정비 후에도 App과 HTTP 서버에 여러 책임이 모여 있었다. 파일 개수를 늘리는
것이 아니라 수정 지점을 찾기 쉽게 만들고 저장·출력의 동작은 유지하는 것이 목적이다.

## 선택

프런트엔드는 app(화면 조립), features(기능별 UI/로직/스타일), shared(작은 공통 코드)로
나눈다. App은 문서 전환과 기능 간 연결을 조정하고 저장 직렬화는 useDocumentSession이
맡는다. DOM 편집 상태는 DocumentEditor에 남긴다. 화면 패널은 전달받은 상태를 표시하고
콜백을 호출한다. 새 상태 라이브러리나 문서 JSON 모델을 도입하지 않는다.

서버 진입점은 경로·토큰·서비스 생성·listen/종료만 수행한다. 라우터에는 서비스를 명시적으로
전달하고 저장소·키별 큐·파일 교체·PDF 출력을 독립 모듈로 둔다. 기존 API와 파일 형식은
그대로 유지한다. DB 도입은 이 변경과 무관하다.

## 대안과 한계

포맷만으로는 상태 소유자와 I/O 경계가 드러나지 않는다. 반대로 전체 재작성이나 프레임워크
전환은 회귀 범위를 키운다. 점진적인 함수 추출과 기능별 배치를 선택했다.

App에는 문서 전환·AI 적용 조정과 일부 모달이 남아 있으며 라우터에는 복원·원본 반영의
조정 코드가 남아 있다. 무조건 파일 길이에 맞춰 쪼개지 않았다. DOM 편집 엔진의 명령들은
하나의 undo/change 경로를 공유하므로 이번에는 임의로 여러 상태 소유자로 나누지 않았다.

## 검증 경로

test/storage.test.mjs로 저장 버전·충돌·원본 보존과 큐 오류 후 진행을 검증한다.
기존 브라우저 테스트로 편집, 문서 전환, 모드 전환, AI 제안 적용, PDF를 확인한다.
테스트 수행 결과는 PR에서 대상 커밋과 함께 기록한다. 작성자의 가독성 판단은 자동 테스트로
대체할 수 없다.
